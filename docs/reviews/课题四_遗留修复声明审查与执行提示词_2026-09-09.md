## 二、关键发现及证据

以下区分源码能够直接确认的问题与尚未在真实 PostgreSQL 上复现的并发时序。未把静态推演写成已完成的数据库实验。

### R1｜P1：删除事务的锁定顺序仍允许旧任务写回

位置：`internal/application/repository/learning.go:640`、`:665`、`:695`。

`DeleteProfileData` 先逐表删除，再写停采设置，最后才更新代际。`ApplyTopicMapping` 则先锁代际行，再写个人数据；代际行不存在时允许继续，实际没有锁到共同控制行。

可行时序，需用真实 PostgreSQL 双连接验证：

1. 选择个人数据为空的主体，删除事务完成各表 DELETE，暂停在代际更新之前。
2. 一个删除前已取得旧代际的映射任务进入事务，读到旧代际，写入映射、事件和状态并提交。
3. 删除事务更新代际并提交；之前完成的 DELETE 不会自动重新扫描，第二步写入的数据可能留存。

这适用于已有代际行的主体；初次使用尚无代际行时，还存在 `FOR UPDATE` 无行可锁的问题。反向锁顺序也应检查死锁风险。事务原子性保证“本事务全成或全败”，并不自动使这些事务按预期串行。

PostgreSQL 明确说明 `FOR UPDATE` 锁定被查询取得的行，Read Committed 的后续命令可以使用新的快照。此处推演依据官方[显式锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)及[事务隔离文档](https://www.postgresql.org/docs/current/transaction-iso.html)。本轮没有运行真实 PostgreSQL 并发实验。

此外，代际保护集中在 `ApplyTopicMapping`。例如 `agentread.go:106` 直接追加事件，`read.go:746` 的作答路径直接追加事件，`backfill.go:149` 直接追加回填事件；`reconcile_runner.go:544` 直接覆盖状态。进入操作前的缓存停采检查不能拦住检查之后发生的删除。`read.go:987` 的停采设置更新也没有与所有写入共用同一数据库控制边界。

必须区分：删除完成后用户主动发起的新操作，在 `optOut=false` 时可以合法建立新画像；删除前已启动的旧工作不能在删除完成后写回。不能用“永远禁止再写”掩盖这个问题。

### R2｜P1：证明删除代际有效的专项测试没有进入有效映射路径

位置：`internal/application/service/learning/maintenance_test.go:460`，对照 `topicmap.go:111`、`:137`。

`TestTopicMappingDiscardedWhenProfileDeletedMidFlight` 提供的是：

```json
{"mappings":[{"topic":"rag","slug":"concept/rag","confidence":0.9}]}
```

真实响应结构读取的是：

```json
{"maps":{"rag":{"slug":"concept/rag","confidence":0.9}}}
```

未知字段被普通 JSON 解码忽略，`Maps` 为空，`acceptedTopicMaps` 不会给出可写入映射。因此，即使没有正确拦截在途写入，该样例仍可得到“没有映射、没有事件、没有新增掌握度”的结果。它使用的还是 `maintenanceFixture` 中的内存仓库替身，不是 PostgreSQL 并发集成测试。

应保留真实 SQLite 触发器回滚测试的价值，但不能用它补足这个服务测试或 PostgreSQL 锁协议的证明。

### R3｜P1：证据版本保护存在等待窗口和永久漏检分支

位置：`maintenance.go:442`、`:471`、`:495`、`:506`；`read.go:569`、`:793`。

`TakeQuiz` 与 `findQuizItem` 校验 `active` 状态，没有将题目哈希与当前证据版本核对。因此，“维护已将题目标记 stale 后两端拒绝”成立，“材料变了就不会再按旧题计分”不成立。

更严重的是，页面无 `ChunkRefs`、读取结果中无非空证据时，维护在 stale 检查之前直接跳过；已经消失、未被页面列表返回的节点也不会进入该检查。旧题可能一直保持 active，而非最多延迟一轮。暂时读取失败和已经确认材料删除应采用不同处理方式，不能一律跳过并继续提供不确定的计分。

生成期间也缺少发布前版本复核：模型调用期间材料改变，返回结果仍可携带旧摘要写成 active。

另有 P2 缺口：`questionsBySlug` 在失效前填充，失效后没有同步移除旧题干（`:464`、`:548`）。新版证据若需要生成同题干、不同答案或解释的题，新题在本轮会被旧去重集合拒绝。因此“同一轮补齐”并非普遍保证。

### R4｜P1：多个旧节点合并到同一节点会相互覆盖

位置：`reconcile.go:33`、`:41`、`:46`、`:60`；`reconcile_runner.go:416`、`:427`；仓库 `learning.go:390`。

构造 `A→C`、`B→C`，A、B 均有不同历史，C 没有状态。`ReconcileSlug` 根据同一个旧 `states` 快照分别产生“C=A”和“C=B”。执行两个 `MigrateMastery` 后，后一次 upsert 覆盖前一次，两条源状态都被删除。C 原本有状态时，则会得到最后一份“B+C”，依然漏掉 A。

前置 `repairFoldDrift` 对存在待迁移来源的目标主动跳过，不能在这一轮补救。下一轮在别名和历史仍保留时可能修回来，但这不是本轮正确合并的保证。

单来源事务修复了中途失败的半完成状态，却没有修复合并算法。应以最终规范节点为单位，把所有来源事件归并、去重、排序、折叠一次，再原子提交整组迁移。

### R5｜P1：每日重放仍可覆盖新状态或恢复已删除画像

位置：`reconcile_runner.go:402`、`:411`、`:482`、`:544`。

重放读取历史后在事务外计算，最终无条件 `UpsertMastery`。若计算期间前台追加有效事件，旧重放结果可以覆盖较新的掌握度；若期间完成画像删除，它可以重建已删除状态。**这在单实例中也成立**，不应仅写进“多实例部署说明”。

另有几个需要收敛声明的边界：

- 分页读取顺序包含 id，但转成 `Event` 后丢弃 id；别名迁移先分组再合并，只按时间排序，同时间跨来源事件无法保证仍按数据库 id 顺序。
- 当前没有贯通的投影算法版本和提交位置/快照版本。删除代际、题目证据哈希都不能替代投影版本。
- `listAllEventsPaged` 将全部页累积到内存，且整轮有 30 秒超时。准确描述是“去掉了 10,000 条硬截断”，不是“任意大小历史均能完成”。
- 主体发现仍依赖已有掌握度及跳过记录。只有事件、首条 fold 未落库的主体不一定被每日任务发现。

应优先修复安全提交、规范合并和事件发现。完整流式检查点可根据实测规模后置，但不能继续宣称已经交付。

### R6｜P2：晚到事件及资格泄漏测试缺少有效反例

`reconcile_paged_test.go:63` 使用 `+1,+1,+2`，且最终只比计数及最早/最晚时间。这些值原本已由 `FoldEvent` 的边界更新和计数规则保证不依赖到达顺序；测试没有先证明存在漂移，也没有比较 `Logit`、`Stability` 等完整结果。即使重放不修复，该样例也不能证明预期的收敛能力。

`cmd/learning-bench/replay_leakage_test.go` 的 `TestOnlineReplayHasQuizDoesNotLeakFuture` 把 B 设为候选宇宙外的首次触达节点。即便未来出题资格泄漏，B 也会因不在宇宙内而无法命中，所以它没有单独验证 `HasQuiz`。候选宇宙测试有价值，不能用它替代资格测试。

必要验收方法：正向对照证明路径确实可达；修复前反例确实失败；临时绕过目标保护时对应测试必须失败。不能只看测试名称和绿色结果。

### R7｜P1（评测结论）：replay 仍未忠实评估生产推荐器

位置：`cmd/learning-bench/replay.go:169`、`:231`、`:239`、`:271`、`:421`；`internal/application/service/learning/bench_export.go:23`；对照生产组装 `read.go:482`。

1. 状态、热度等仍仅以 slug 为键。一个用户的多个知识库有同名节点，或混合多个主体的导出，都会合并上下文。应按 `(tenant_id,subject_id,knowledge_base_id)` 分流，图至少按所属租户和知识库筛选。
2. Bench 输入虽有 `DirectFacts`，两种 replay 调用都未填充；生产使用的自评、跳过、材料顺序、最近路径等也未完整传入。复用排序函数不等于评估了实际输入条件下的生产策略。
3. 热度、亲和及后缀真值没有事件类型白名单，`agent_read`、后台话题映射等也可能成为“下一步看什么”的标签。这改变了评估对象。
4. `input.Edges`/`edges` 直接用于过去时刻，没有图版本或截至时刻的有效性校验；使用当前导出的边时，不能保证无未来结构泄漏。
5. 排序只用 `OccurredAt`，80/20 按条数切分可能拆开同时间事件组。需要明确同时间批次的“先预测、后统一吸收”或其他因果协议。
6. 只用过去触达节点构造候选集，是缺少历史页面快照时合理的受限协议，但它无法评价对“已存在、尚未读过的节点”的主动引导。报告应明确这是已观察节点上的行为预测代理任务。

建议保留已修的前缀宇宙、冻结时钟、在线增量资格；在修复以上问题后重新产出结果。不要沿用旧分数证明新算法优越。

### R8｜P2：Agent 来源拆分未贯通所有消费者

`agentread.go:106` 的零权重与阅读窗口隔离值得保留。不过仓库 `learning.go:145` 的 `ListLastActivity` 对所有事件求最近时间；replay 的计数、亲和与目标也未过滤 Agent 事件。

因此“不会增加掌握度或占人类首读权重”可以确认，“仅时间线留痕、对其他视图和评估完全无影响”不准确。应明确每种事件是否参与人类活动、能力、保持、推荐上下文和评测目标，而不是只给权重赋零。

## 四、下一步算法选择

**当前优先级是修正证据语义、状态生命周期和评估真实性，暂不整体替换学习模型。** 本轮源码审查不能证明存在对当前数据条件“十分优越”的某个算法，也没有新做算法效果实验。

- 关联：保留确定性引用归因、候选召回和受约束模型裁决。先用人工标注集测归因精度/召回、别名误合并和先修边误报，再决定是否更换召回或重排。未测量前不应只因模型更复杂而换型。
- 度量：最值得下一阶段投入的是活动、能力、保持的证据分离。浏览和工具访问不应直接充当能力增长或延迟保持的证据；已有测验门槛继续保留。完整三通道不是修正删除协议的前置条件。
- 引导：先让离线适配器忠实重建生产输入，并增加先修约束违反率、无有效材料推荐率等直接质量指标。行为预测的 HitRate/MRR 只能作为代理指标。
- 展示：维持已有图谱和学习面板，检查零权重后台事件是否仍改变“本人最近学习”等解释。此阶段不建议无证据地重做界面。

只有拥有足够的独立作答、延迟作答和材料版本数据后，才适合比较更完整的记忆调度或知识追踪模型；其成本、校准和留出集结果应决定选型。不要将当前启发式稳定性公式描述为已经训练、校准的完整 FSRS，也不要把未经校准的分数写成真实掌握概率。

课题交付至少应选一个主切入角度形成可追溯的有效性证据。没有真实受试者时，可以如实交付独立标注的关联/先修关系评估与协议严谨的代理实验；若主张“提升学习效果”，仍需独立前后测或延迟测，不能由代码单测代替。具体样本量应根据研究目标设计，不在报告中编造达标数字。

### 阶段 A：修复控制边界，并让关键测试真正命中风险

涉及仓库 `learning.go`、服务采集/作答/回填/维护/重放路径及相关测试。

1. 修正删除期间模型返回测试的 JSON 格式。添加“不删除时同一有效返回确实产生映射、事件、状态”的正向对照；确保旧代际路径确实触发栅栏拒绝，不能仅断言最后没有数据。
2. 为同一主体建立可锁定的数据库控制记录，处理记录尚不存在时的初始化竞争。删除和所有相关写入采用一致锁顺序；在事务开始后、访问个人数据之前取得共同控制边界。不要仅把 FOR UPDATE 添加到原位置。
3. 建立清晰的操作代际语义：旧任务带旧代际，新操作读取新代际；事务内复核代际和必要的当前停采状态。缓存只用于快速路径，不能承担最终保证。
4. 枚举所有个人数据写入者，至少包括人类阅读、Agent 阅读、引用、测验尝试/事件/状态、话题映射、回填、跳过/自评、每日重放和迁移。核实每一项的原子性、幂等和删除/停采覆盖，不接受仅修模型映射。
5. 测验等一个逻辑操作的尝试记录、事件及状态应保持一致；失败时回滚或采用有证据支持的等价恢复协议，不能把每日任务当作无条件兜底。

验收：真实 PostgreSQL 两个独立连接，通过可控屏障覆盖“删除先清扫、写入后提交”、相反顺序、无控制行首次并发、删除 optOut=false、仅停采、删除后新操作合法恢复。保留 SQLite 回滚用例。暂停重放后删除，再恢复重放，不得重建旧画像。尚无 PostgreSQL 测试环境时明确标注该项未验收，不得用 SQLite 或 -race 替代。

### 阶段 B：修复规范节点合并和重放的安全提交

涉及 `reconcile.go`、`reconcile_runner.go`、事件/状态类型和仓库事务。

1. 按完整作用域及最终规范节点分组，将所有旧别名和目标历史统一去重、排序、折叠，再按整组事务提交；作答记录、跳过记录及其他相关引用需保持一致。明确事件保留原始 slug 时如何长期恢复规范归属，不能依赖可能消失的临时别名。
2. 贯通 `(occurred_at,id)` 顺序；遇到同时间事件不得在分组或合并中丢失排序键。不要通过随意叠加各节点 logit 合并历史。
3. 为重放建立稳定的处理范围和条件提交规则，避免覆盖计算期间的新事件/状态。区分删除代际、算法版本、输入快照/处理位置，记录能够解释一次投影结果的信息；位置选型必须能处理晚到旧时间事件。
4. 发现只有事件但无投影的主体。去掉“任意大小完成”的过强承诺；对大历史给出超时、内存和续跑策略，按实测决定是否必须流式化。

验收：A/B 同时并入 C，覆盖 C 原有/无状态、不同迭代顺序、同时间正负事件、第二次重跑、组内故障回滚。晚到事件样例必须先证明到达序与规范重放的状态不同，再证明修复后所有字段收敛。另测分页边界、超过旧上限的历史、重放中新增事件、重放中删除、只有事件无状态。测试临时绕过目标修复时应失败。

### 阶段 C：让题目可用性真正绑定当前证据

涉及 `maintenance.go`、`quizgen.go`、题目读取和提交路径、题库仓库。

1. 明确证据版本和题目发布的生命周期。采用材料更新时失效、接口版本校验或等价的可靠方案，使材料改变后的旧题无法继续增加掌握证据；兼顾读取成本，避免每次全库重算。
2. 覆盖页面被删除、类型不再可出题、引用清空、全部 chunk 消失、旧空哈希、读取暂时失败。区分确定无效和暂时无法验证，后者不能被当作已验证的有效证据计分。
3. 模型返回后、发布前复核生成快照。生成期间材料变化则放弃过期结果或重试，不能新发布旧版本 active 题。
4. 同步维护 active 数量和题干去重集合。允许新版证据下合法的同题干新版本；保持人工停用状态，不能因自动再生悄悄恢复人工判坏题。
5. 明确已下发后失效题的提交反馈、旧作答审计保留和后续能力门槛策略。不得简单删除历史尝试掩盖版本差异。

验收：真实修改材料后，在维护前请求题目和提交旧答案；清空引用/删除证据后运行维护；满额题库变更；模型返回前修改材料；同题干新版本在当轮生成；人工停用不会被误恢复。断言题目状态及掌握证据均符合策略，而非仅手工将题置 stale 后测拒绝。

### 阶段 D：重建可信评测及可交付文档

涉及 `cmd/learning-bench`、`bench_export.go`、生产推荐输入组装、活动查询及文档。

1. replay 以完整作用域分流；分别构造每个主体、知识库的历史，禁止同名 slug 跨域混合。
2. 明确事件消费者白名单。Agent 和后台事件不得作为人类下一步行为真值或人类热度；它们是否能作为其他推荐上下文必须有明确语义。检查最近活动视图，与“仅时间线”声明一致。
3. 从截至预测时刻可见的历史恢复生产所需直接测验事实、自评、跳过、材料和最近路径等输入；缺少数据时缩小结论范围或明确拒绝声称生产等价，不能默默以空值代替。
4. 用历史页面/题库/边快照定义资格。没有快照时保留受限代理协议并明确限制。规范同时间批次、迟到数据的可见性和 split 规则。
5. 三个 ranker 采用明确且可比的候选资格；随机源独立并固定种子。静态推荐应固定其静态输入和随机性，或明确声明重复采样协议。输出覆盖率、不可达真值、按用户/知识库汇总及必要的不确定性，不只给一个总分。
6. 修正 HasQuiz 测试：B 已在前缀宇宙中但当时无题，只改变未来题目事件；直接断言预测时刻输入未获得未来资格。增加未来图变化、Agent 注入、跨知识库同名节点和同时间事件排列的测试。
7. 修复声称支持的导出格式读取。真实运行验证命令，更新受版本控制的设计和验收文档，确认云端新克隆能取得必要文档、迁移和测试。不要只更新被忽略的 hls 文件。

验收：修复前后的同协议对照、独立留出数据、生产/离线输入一致性样例、无未来信息回流的反例测试。报告必须写清代理任务与学习效果的区别，不捏造受试者、样本或显著性，不以合成数据通过证明真实学习收益。

### 最终交付格式

逐条报告：问题编号、实际触发条件、修改位置、修复前反例、修复后结果、未验证边界。列出实际运行的命令与结果，将既有测试、专项回归、数据库并发验证和用户效果实验分开。先关闭 R1/R2/R4/R5，再完成题目版本和评测；R6 的测试改进随对应修复同步进行。任何关键用例未触发目标路径、未做正向对照或所需环境未验证时，不得再宣称“四项全部深度完成”。

## 六、可接受的收尾条件

可以将这轮修复标记为完成的最低条件是：删除及停采不会被旧工作绕过；单实例后台不会覆盖前台新证据；多源归并无丢失；失效材料不会产生新的有效计分；专项测试真正能区分有无修复；评测明确且忠实描述所测对象；交付文件可从版本库复现。

完整三通道、学习模型替换、大规模用户试验可以按研究计划推进。若不做，就相应收窄产品与论文的效果主张；不能用这些较大的开放项掩盖本轮仍可具体修正的正确性缺陷。
